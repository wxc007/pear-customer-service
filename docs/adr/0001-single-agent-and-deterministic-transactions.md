# ADR 0001：单 Agent 与确定性业务事务边界

- 状态：已接受
- 日期：2026-11-03

## 背景

智能客服需要以自然语言连续咨询，并读取实时商品信息。生成式模型的输出具有不确定性，而商品、订单、支付和售后业务要求明确的授权、状态与持久化结果。若让模型直接管理数据库事务或把自然语言当作执行凭证，会产生越权、重复写入和伪造成功等风险。

## 决策

系统只设置一个智能客服 Agent。Agent 负责理解意图、组织受限上下文、调用服务端白名单工具和生成回答，不设置多个自主 Agent 协作。

业务事实与业务事务由确定性服务端代码负责：

1. 模型不能访问数据库、执行任意 SQL 或 URL、读写文件或运行系统命令。当前仅登记 `listSpus` 与 `getSku` 两个只读商品工具，工具内部调用公开目录服务实时查询。
2. 用户消息、历史摘要、知识资料和工具结果都视为不可信数据，不能修改系统规则。动态价格、库存和可售状态不能以模型记忆或摘要为依据。
3. 会话与消息使用独立、短小的数据库事务。开始一轮对话时，先保存用户消息和 `STREAMING` 回复占位，再启动模型流；完整非空回复保存为 `COMPLETED` 后才发送 `complete`；模型异常、超时或空白回复保存为 `FAILED` 后才发送 `error`；客户端取消流时也写入失败终态。
4. 不跨越整个模型流保持数据库事务。SSE 断线不表示业务操作已完成，历史消息接口用于恢复已经持久化的结果，不承诺从原流断点续传。
5. 后续订单、支付、售后等写工具必须在工具内部重新完成身份、归属、权限、参数、状态机与幂等校验。需要用户确认的操作采用独立的两阶段确认，模型输出不能替代确认凭证。
6. 模型超时、不可用或工具失败时返回明确失败，不自动把不确定的模型调用重放为业务写入，也不伪造商品信息或业务成功。

## 上下文与摘要

全量消息始终保存在 MySQL。单次模型请求只使用最近 20 条非流式消息以及滚动摘要。当前摘要是服务端对超出窗口消息生成的确定性压缩文本，不额外调用模型；它只用于保持对话背景，不能作为动态业务事实源。

## 后果

- Agent 可以独立替换模型提供方，业务事务边界不随模型能力变化。
- 流式回复可能已发送部分增量后失败，因此最终状态必须以历史消息中的 `COMPLETED` 或 `FAILED` 为准。
- 当前滚动摘要是有损压缩，长会话中的早期细节可能需要用户重新确认；订单等关键业务对象后续必须依赖结构化业务记录，而不是摘要。
- 每次新写工具都需要显式审查权限与事务边界，不能因模型可调用而默认获得授权。
