# ADR 0002：MySQL 业务事实与 Qdrant 可重建向量索引分离

- 状态：已接受
- 日期：2026-11-04

## 背景

政策、储存和食用回答需要语义检索及可追溯来源，但向量相似度不能代替文档发布状态、版本和索引状态。动态价格、库存、订单等事实也不能写入静态知识库，否则会产生过期答案。Qdrant 故障或嵌入模型不可用时，系统仍需保持诚实，不能把模型记忆当作可靠资料。

## 决策

1. MySQL 保存知识文档、版本、完整原文、分段、稳定向量 ID、发布状态、索引状态、索引错误和时间。Qdrant 只保存可删除、可重建的向量及必要定位元数据，不作为事实源。
2. 每个分段使用稳定 UUID 作为 Qdrant 点 ID。索引写入是幂等 upsert；状态按 `PENDING → INDEXING → INDEXED` 流转，异常记录为 `FAILED`。外部向量调用不包裹在长数据库事务中。
3. 检索默认请求最相关的 5 个片段，并通过 `app.knowledge.similarity-threshold` 排除低相关结果。向量返回后仍须回查 MySQL，只有 `PUBLISHED` 且 `INDEXED` 的版本可以进入模型上下文。
4. 来源标题和版本号从 MySQL 读取，并在完整答复持久化前由服务端附加。模型不需要凭记忆生成引用，历史消息可以恢复相同来源。
5. 检索不足时直接返回不确定，不调用模型拼凑相似但不相关的资料。Qdrant 或嵌入模型不可用时返回知识暂不可靠的失败结果，不产生政策承诺。
6. 价格、库存、订单等动态事实继续使用实时业务工具，不进入静态知识检索替代链路。知识文档中的命令式文字仅作为不可信资料，不能增加工具权限。
7. 演示环境只初始化明确标记的已发布资料；非演示环境不自动插入。管理端版本发布、停用和索引重建由后续工单实现。

## 故障与恢复

- 应用启动时向量写入失败只更新索引状态，不阻止其他业务启动。
- 已索引版本在 Qdrant 故障时不能被视为当前可回答依据；查询失败必须明确降级。
- Qdrant 数据丢失后，可根据 MySQL 中的版本、分段和稳定向量 ID 重建。重建完成并校验前不得把版本标记为 `INDEXED`。
- MySQL 与 Qdrant 之间不追求分布式事务；以 MySQL 状态门控和可重放索引流程处理短暂不一致。

## 后果

- 检索需要向量查询与少量 MySQL 状态回查，但获得了明确的来源与发布控制。
- 嵌入模型需要单独可用；未配置时应用可以启动，知识问题会诚实降级。
- 当前演示分段为人工维护，后续运营接口必须保持同一事实模型与状态门控。
