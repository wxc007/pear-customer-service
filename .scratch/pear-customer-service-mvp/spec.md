# 梨产品智能客服 MVP

Status: ready-for-agent

## Problem Statement

顾客在选购鲜梨及梨制品时，需要同时了解商品规格、储存和食用方法、价格库存、配送范围以及差异化售后政策。传统静态客服只能回答问题，不能可靠地协助加购、下单、查询物流或提交售后；完全依赖生成式模型又可能编造业务事实、重复执行操作、越权访问订单或擅自承诺赔付。

商家还需要在售后争议、模型故障和超出智能客服权限时，由人工客服接管会话，并保证商品、订单、支付、发货、售后和知识资料都有真实、可追溯的业务记录。

## Solution

构建一个独立的梨产品智能客服后端，提供游客咨询、登录顾客交易、流式会话、商品与知识检索、购物车、订单、沙箱支付、发货、售后、人工接管及运营管理能力。

智能客服负责理解意图、组织回答和调用白名单业务工具；价格、库存、订单、支付、物流和售后状态必须来自实时业务数据，政策和商品说明必须来自已发布的知识资料。模型不作为业务事实源，也不能直接访问数据库或绕过交易确认、权限校验、状态机和幂等控制。

系统采用模块化单体，以 MySQL 保存业务事实，以 Qdrant 保存可重建的知识向量索引，以 MinIO 保存私有售后图片。项目附带简易联调页面、演示数据、OpenAPI 文档和基于外部行为的主流程测试，但不包含正式生产级前端、真实资金支付或真实物流服务商集成。

## User Stories

1. As a 游客, I want 无需登录即可咨询梨产品, so that 我可以先了解商品再决定是否注册。
2. As a 游客, I want 通过 SSE 逐步看到智能客服回答, so that 我不必等待整段回答生成完毕。
3. As a 游客, I want 获得后端签发的匿名会话凭证, so that 我可以安全地继续当前会话。
4. As a 游客, I want 登录后绑定当前会话, so that 我登录前的咨询上下文不会立即丢失。
5. As a 顾客, I want 使用用户名和密码注册及登录, so that 我可以使用购物、订单和售后服务。
6. As a 顾客, I want 安全地刷新和退出登录凭证, so that 我的账号不会被长期有效的凭证暴露。
7. As a 登录用户, I want 查看自己的历史会话和消息, so that 我可以追溯之前的咨询与操作结果。
8. As a 登录用户, I want 创建相互独立的新会话, so that 新任务不会误用旧会话中的订单或售后对象。
9. As a 顾客, I want 系统拒绝访问他人的订单、售后和会话, so that 我的个人数据不会被越权查询。
10. As a 顾客, I want 按 SPU 浏览梨产品并选择具体 SKU, so that 我能明确购买品种、净重和包装。
11. As a 顾客, I want 查看鲜梨的品种、产地、果径和储存说明, so that 我可以判断商品是否适合我。
12. As a 顾客, I want 查看梨制品的配料、规格、保质期和食用说明, so that 我可以做出知情的购买决定。
13. As a 顾客, I want 获得实时价格和可售库存, so that 我不会根据过期信息下单。
14. As a 顾客, I want 下架商品无法通过旧购物车继续购买, so that 我不会购买已停止销售的商品。
15. As a 顾客, I want 查询收货地区是否可配送及应付运费, so that 我能在下单前了解完整履约条件。
16. As a 顾客, I want 商品营养和食用回答有已维护资料依据, so that 我不会受到夸大功效或医疗建议误导。
17. As a 顾客, I want 登录后将具体 SKU 和数量加入购物车, so that 我可以继续比较后再购买。
18. As a 顾客, I want 重复加购同一 SKU 时合并数量, so that 购物车不会出现无意义的重复商品行。
19. As a 顾客, I want 在超过数量或种类上限时得到明确提示, so that 我可以自行调整购买意向。
20. As a 顾客, I want 勾选部分购物车商品下单, so that 我可以保留暂时不买的商品。

22. As a 顾客, I want 在创建订单前看到 SKU、数量、收货地址、商品金额、运费和应付总额, so that 我可以明确确认交易内容。

## Implementation Decisions

### 项目与架构

- 创建独立的 Maven 项目，使用 JDK 17、Spring Boot、Spring AI，Maven 坐标为 `com.pear:pear-customer-service`，根包为 `com.pear.customerservice`。
- 采用单模块、按业务领域分包的模块化单体。领域边界包括认证与顾客、会话与 Agent、商品与库存、购物车、订单与支付、发货、售后、知识库、人工客服和运营管理。
- 使用 Spring Web、Validation、Security、Data JPA、Spring AI、Flyway、MySQL、Qdrant、MinIO、springdoc-openapi、Actuator/Micrometer 和 Lombok。
- 使用同一套稳定且相互兼容的 Spring Boot 与 Spring AI 依赖管理，不迁移旧示例中的混合 SNAPSHOT/Milestone 配置。具体版本在实施时依据官方兼容性核实并锁定。
- 不引入 Redis、消息队列、Quartz、MapStruct、Resilience4j、微服务或多模块 Maven 工程。
- 数据载体使用普通 class，不使用 Java record；不使用 `var`。业务编排、异常、依赖注入、换行及测试风格遵循项目全局代码规范。

### 数据与基础设施

- MySQL 使用 8.4 LTS、InnoDB、`utf8mb4`，保存全部业务事实及知识文档事实源。
- Qdrant 通过 Spring AI Vector Store 保存知识向量索引；索引可以从 MySQL 中已发布的知识文档重建，不保存订单、库存等动态业务事实。
- MinIO 使用私有桶保存售后图片，MySQL 只保存文件元数据及对象关联。
- 使用 Spring Data JPA 持久化，Flyway 管理全部结构变更，Hibernate 仅校验结构而不自动建表或改表。
- 金额使用 `BigDecimal` 和 MySQL 定点小数，禁止浮点金额计算；时间以 UTC 保存，接口使用 ISO 8601，业务展示默认采用 Asia/Shanghai。
- 内部主键使用 Long；订单、支付、售后等对外编号使用不可预测的唯一业务编号。业务编号不可预测不能替代权限校验。
- Docker Compose 只负责本地 MySQL、Qdrant 和 MinIO；应用可通过 Maven 或 IDE 启动。配置示例脱敏，不创建或修改保存真实密钥的环境文件。

### 核心领域模型

- 商品按分类、SPU、SKU、库存建模。SPU 区分鲜梨与梨制品，共同字段直接建模，差异属性使用 MySQL JSON。
- SPU 和 SKU 均有独立上下架状态，只有两者均可售时才能购买。可售库存等于现存库存减去预占库存，所有库存变化保留变更记录。
- 登录账号、顾客资料和收货地址分开建模。每个顾客可有多个地址及一个默认地址，订单保存收货地址和联系电话快照。
- 每个登录用户只有一个有效购物车；同一 SKU 合并数量，每行最多 99 件、最多 50 种 SKU。购物车不预占库存，支持勾选部分商品行下单。
- 订单、订单商品行、支付单、发货单、退款单和售后申请分别建模。订单保存商品、价格、地址等成交快照。
- 会话、消息、人工接管记录、业务操作确认记录和操作审计分别建模；模型上下文摘要与真实业务执行记录分离。
- 知识文档按文档、版本和分段内容建模。只有发布且向量化成功的版本参与回答，旧版本可以追溯但默认不参与当前检索。
- 所有关键管理操作记录操作者、时间、业务对象、结果及关联请求，敏感数据不无差别复制到审计内容。

### 订单、支付与履约状态

- 订单主状态为待支付、待发货、已发货、已完成或已关闭。支付、发货和售后状态独立维护，不创造相互混合的组合状态。
- 创建待支付订单时通过数据库事务预占库存；取消或超时关闭释放预占，支付成功转为实际扣减。库存不足或商品下架时创建失败。
- 待支付订单 30 分钟未支付自动关闭；支付前可以取消，支付后只能通过售后处理。
- 支付失败后允许重新发起，但同一订单最多一个处理中的支付单。支付通知必须验签和防重复。
- 订单关闭与支付成功使用数据库条件更新竞争。已关闭订单收到支付成功时进入支付异常并转人工，不能静默忽略。
- 首期一个订单只有一张普通发货单，不支持拆包裹。发货单保存承运方、物流单号、发货时间、物流状态、最后更新时间和收货时间。
- 顾客可确认收货；发货满 7 天未确认则自动完成。补发使用关联售后申请的独立发货单，不创建有支付金额的新订单。
- 定时任务使用 Spring Scheduling 和数据库条件更新，基于单实例部署前提实现，重复运行不得产生二次副作用。

### 售后规则

- 售后类型包括仅退款、退货退款和补发。状态至少覆盖待审核、审核通过、已拒绝、等待退货、退款处理中、已完成和已撤回。
- 鲜梨不支持无理由退货，签收后 24 小时内可申请品质售后；梨制品支持符合条件的 7 天无理由退货，质量问题可在保质期内申请。
- 同一商品行不能同时存在多个处理中的售后，累计退款不能超过该行实付可退金额；部分售后记录具体数量和金额。
- 智能客服可以校验条件、整理凭证和提交，不能批准退款、退货或补发。明显超时或重复申请可以自动拒绝，所有资金和补发批准均由人工完成。
- 已支付未发货仅申请退款，成功后释放预占库存；鲜梨品质问题原则上不寄回；梨制品无理由退货在退回验收后退款。
- 品质问题及错发由商家承担处理费用，梨制品无理由退货由顾客承担退回运费。
- 退款原路退回，沙箱支付同样保存退款单与状态。品质问题商品不能自动恢复为可售库存。

### Agent、工具与会话

- 使用单智能客服 Agent，结合 Spring AI ChatClient、Tool Calling 和 Advisor。不实现多个自主 Agent 协作。
- 模型只能调用服务端白名单业务工具，不能执行任意 SQL、URL、文件系统或系统命令，也不能直接访问数据库。
- 工具执行时重新校验认证身份、资源归属、角色权限、参数和业务状态，模型输出不能替代服务端授权。
- 用户消息、知识文档和工具结果一律作为数据处理，忽略其中试图改变系统规则、窃取信息或调用非授权能力的指令。
- 加购等低风险操作在用户明确提出后可直接执行；创建订单、取消订单和提交售后采用两阶段交易确认。
- 交易确认先返回操作摘要和有效期 5 分钟的确认凭证，确认时重新校验业务状态。凭证绑定用户、会话、操作类型和业务对象。
- 写接口使用幂等键、唯一约束及条件更新防止重试重复执行。模型、SSE 或网络超时不得触发业务写工具自动重放。
- 全量会话和消息持久化；模型上下文默认使用最近约 20 条消息、滚动摘要和当前业务上下文，动态事实仍实时查询。
- 游客凭证有效期 24 小时，登录后可绑定当前会话。新会话不默认沿用旧会话交易对象。
- 每个环境只启用一个模型提供方。DeepSeek OpenAI 兼容接口为首选，Ollama 为可切换配置；不自动跨供应商降级。
- 模型超时或不可用时不得编造答案，可进行安全重试并允许转人工；只有成功持久化的请求才能向用户宣称提交成功。
- 发送给模型的数据遵循最小化原则，不发送完整认证信息、内部审计或不必要的地址和手机号。敏感确认明细优先后端结构化生成。

### 知识检索

- 动态业务事实走实时工具查询；政策、储存和食用说明走已发布知识资料检索。
- 默认检索最相关的 5 个片段，相似度阈值可配置并通过演示数据回归调整。
- 检索结果不足时明确不确定并可转人工，不能用相似但不相关的资料凑答案。
- 政策回答提供文档标题和版本等来源信息。首期不自动联网搜索或抓取网页。
- 支持手动录入以及 Markdown、纯文本导入；不支持任意 Office、PDF 或网页解析。
- 知识发布流程记录向量化和索引状态。索引重建完成并校验后再切换生效版本，Qdrant 故障不能被视为知识回答可靠的依据。

### 认证、权限与防护

- 使用 Spring Security、JWT 和本地用户名密码注册登录，密码使用 BCrypt。角色包括顾客、人工客服和管理员。
- 顾客访问令牌有效期 30 分钟，刷新令牌有效期 7 天；刷新时旋转旧令牌并只保存哈希，支持退出登录和令牌失效。
- 顾客只能操作本人资源；人工客服只能处理自己认领会话及关联业务；管理员负责商品、库存、配送、知识资料和支付异常。
- 人工客服可审核售后但不能修改商品、运费和权限配置；任何角色都不能绕过状态机或直接改写历史成交事实。
- 单实例内按用户或来源地址限制 AI 消息默认每分钟 20 条；连续 5 次登录失败后暂停该账号登录 15 分钟；上传单独限频，阈值均可配置。
- 售后图片每张申请最多 6 张、单张最大 5 MB，仅允许 JPEG、PNG、WebP；校验扩展名、MIME 和实际文件内容，使用随机对象名。
- 私有图片临时访问地址有效期 10 分钟，访问仅限资源所有者、已授权客服和管理员。
- 演示环境可创建明确标记的演示账号；非演示环境不得启用固定默认密码，初始管理员通过一次性流程设置。

### API、SSE 与联调页面

- API 统一使用 `/api/v1` 前缀，普通接口直接返回资源 DTO，不增加全局响应包装；错误采用 Spring ProblemDetail。
- API 覆盖注册登录、会话与消息、商品查询、购物车、交易确认、订单与支付、发货与物流、售后与凭证、人工接管、知识资料和运营管理。
- SSE 事件至少区分文本增量、待确认操作、业务执行结果、转人工、完成和错误。必要的业务结果先持久化再发送。
- SSE 断线后通过历史接口恢复，不承诺从原流断点继续。所有事件保持明确的会话和消息关联。
- 简易联调页面使用 Spring Boot 托管的原生 HTML、CSS 和 JavaScript，支持游客/登录、流式聊天、商品展示、订单确认、售后上传和转人工，不引入 Node.js。
- 提供 OpenAPI 文档，接口权限、字段限制和错误语义与真实服务端行为一致。

### 可观测性、配置与文档

- 提供健康检查、Prometheus 指标及带请求关联 ID 的结构化日志，记录模型调用耗时、工具结果和关键状态变化。
- 日志默认不输出完整聊天内容、手机号、地址、访问令牌、密钥或私有图片地址。
- 演示数据通过独立入口初始化，非演示环境不自动插入。演示商品、政策、支付和物流结果必须明确标记。
- 提供 README、本地启动指南、架构说明、API 说明、演示流程和测试说明。
- 记录两项 ADR：单 Agent 与确定性业务事务的边界；MySQL 业务事实与 Qdrant 向量索引分离的方案。

## Testing Decisions

### 主测试接缝

- 唯一主测试接缝为 `/api/v1` REST 接口和 SSE 事件流，从顾客、人工客服及管理员的外部操作验证系统行为。
- 测试启动完整 Spring 应用，并使用 Testcontainers 提供真实 MySQL、Qdrant 和 MinIO。
- 模型、真实支付和物流外部依赖使用可控替身；沙箱支付适配器本身作为被测业务组件。
- 这是新项目，没有既有业务测试或测试接缝可复用；旧示例的上下文加载测试不作为业务测试先例。

### 好测试的标准

- 只断言外部可见的响应、持久化业务结果、权限拒绝和 SSE 事件，不绑定内部类、私有方法或具体工具调用次数。
- 测试数据自包含，业务期望值直接表达，不在生产代码中为测试提取常量。
- 领域单测只补充库存竞争、金额计算、状态机等复杂规则，不另建 Service 层主测试接缝。
- 模型效果采用独立人工回归，自动化构建不断言不稳定的自然语言全文。

### 必测模块与场景

- 认证与授权：注册登录、刷新旋转、退出、游客绑定、角色矩阵、资源归属和越权拒绝。
- 会话与 Agent：流式事件、有限上下文、无依据拒答、提示词注入隔离、模型故障、敏感数据最小化及转人工。
- 商品与购物车：SPU/SKU 上下架、实时价格库存、数量合并、上限、部分勾选和旧购物车失效。
- 订单与库存：两阶段确认、确认凭证绑定与过期、幂等下单、最后一件库存竞争、预占释放和超时关闭。
- 支付：失败重试、重复通知、关闭与成功竞态、迟发成功进入支付异常，以及沙箱结果的明确标识。
- 发货与售后：确认收货、自动完成、三种售后类型、部分售后、重复申请、撤回、图片限制、退货验收、退款上限和补发。
- 人工客服：队列认领竞争、AI 停止与恢复、关联业务权限、审核和审计。
- 知识库：版本发布、停用、低相关拒答、来源追溯、向量失败、索引重建和 Qdrant 不可用降级。
- 故障与副作用：模型、MinIO、Qdrant 或实时工具故障时不能伪造成功，所有重试不得重复产生资金或库存副作用。

## Out of Scope

- 完整生产级 Web/H5、小程序、App 或运营管理后台。
- 电话、语音、微信公众号、第三方电商平台等多渠道接入。
- 真实微信支付、支付宝、银行账户或真实物流服务商集成。
- 优惠券、积分、会员、拼团、秒杀、复杂促销、订单优惠、发票、企业采购和礼品贺卡。
- 一个订单配送多个地址、拆分普通发货单或复杂多仓履约。
- 多 Agent 自主协作、模型直接数据库访问、自动批准赔付或自动跨模型供应商降级。
- 自动联网搜索、网页抓取、Office/PDF 知识解析平台。
- 图片鉴黄、病毒扫描或其他外部内容审核服务。
- 短信、微信、第三方社交登录、单点登录及复杂设备管理。
- Redis、消息队列、微服务、Kubernetes、多实例、高可用、灾备和正式生产 SLA。
- 自动执行正式部署、对外发布、数据库备份或恢复；HTTPS、正式密钥管理、生产网关和备份策略属于上线前工作。
